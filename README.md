# 会自己找选题的小红书内容创作流

这是一套面向小红书图文的内容创作流。

它的核心作用是：每天自动发现值得写的选题，把热点、产品体验、开箱、吐槽、横评等素材整理成可二创的候选，再经过筛选、定角度、写正文、质检、小红书适配，最后沉淀到飞书多维表格。

它不是一个「给我写一篇」的 prompt 集合，而是一条从找题到复盘的生产链路。

## 它解决什么问题

做小红书内容最难的地方，通常不是写一句漂亮文案，而是前面的判断：

- 今天到底写什么？
- 这个选题有没有传播价值？
- 原始素材在哪里，能不能点开看？
- 用户真实反馈是什么，是种草、吐槽、避坑还是开箱？
- 这个题能不能转成小红书图文？
- 写完以后怎么质检、怎么复盘、怎么沉淀到选题池？

这套流程把这些事串起来，让内容生产不再从空白页开始。

## 它适合谁

适合想持续做小红书内容，但不想每天靠灵感硬撑的人。

典型场景包括：

- 小红书图文选题
- 科技、数码、生活电器产品二创
- 什么值得买体验、开箱、吐槽、横评素材复用
- 热点转观点文章
- 长文改成小红书笔记
- 用飞书 Base 管理每日选题池

如果你只是想让 AI 随便写一篇文章，这套东西会显得重。
如果你想把「找题、判断、写作、质检、复盘」变成每天能跑的流程，它就正好。

## 它怎么工作

主流程是：

```text
抓素材
  ↓
筛选题
  ↓
选角度
  ↓
定结构
  ↓
做标题
  ↓
写正文
  ↓
质检修稿
  ↓
小红书适配
  ↓
写入飞书选题池
```

它有两条上游输入：

1. **热点线**：回答「今天大家在聊什么」。
2. **产品体验线**：回答「最近哪些产品正在被体验、开箱、吐槽、横评」。

两条线不要混在一起。热点适合做观点，产品体验适合做二创。

### 两分钟全覆盖与三次确认

“跑一次内容创作流”默认使用交互模式：

1. 120 秒内并行抓取全部已配置来源；实时失败的来源读取最近有效缓存，并明确标记 `live`、`cache`、`unavailable` 或 `disabled`。
2. 先输出 5-8 个热点候选，等待确认选题。
3. 只研究已确认的选题，输出 2-3 个角度，等待确认角度。
4. 输出标题方向、核心判断和文章结构，等待确认定调。
5. 确认后才写正文、质检、配图和发布。

只有明确说“直接跑完”“全自动”或“不用确认”，才会跳过前三次确认。热点阶段不提前运行 Linkly、zvec、深度网页核验、评论研究或生图。

全量指所有配置来源都必须产生状态，不代表每个上游平台都能实时成功。缓存数据会显示缓存时间，不会伪装成实时热点。

### 小红书账号安全边界

内容创作流永久禁止使用个人小红书登录态，包括 `xhs-cli`、xiaohongshu-mcp、浏览器 Cookie、CDP 登录页和本地小红书 Cookie。即使只搜索公开笔记，也不会借用个人账号。

小红书材料只接受用户主动提供的链接、截图、导出内容，以及无需个人登录态的公开索引。小红书单篇互动量不再自动计入全网热点评分。

## 它会输出什么

产品体验线会产出类似这样的候选：

```text
标题：花3000买咖啡机结果翻车？测评三款千元档，看完知道怎么选不踩坑
链接：https://post.smzdm.com/p/aqrge67p/
类型：吐槽/避坑
二创切入：适合做「咖啡机避坑/翻车复盘」方向
内容定位：买半自动咖啡机后，预热、萃取、奶泡、清洁都可能变成日常负担
```

然后继续二创成小红书笔记：

```text
我终于知道为什么很多人买了咖啡机就吃灰了
```

重点是：只给标题没有意义。选题必须带原文链接、内容定位、互动数据、短摘和二创切入，后面才能真正写出内容。

## 核心能力

### 1. 自动抓产品体验素材

产品体验线会从什么值得买为主的内容源里，抓取科技类和生活类产品的体验、开箱、横评、吐槽、新品信息，再用二创分数排序。

默认主抓词来自什么值得买近期类目热度和实跑结果，不是拍脑袋猜的：

```text
NAS、耳机、键盘、路由器、显卡、显示器、手机、充电器、游戏本
洗地机、咖啡机、扫地机器人、空气净化器、空调、冰箱
浴霸、投影仪、3D打印机、车载冰箱、智能门锁
```

每条候选默认包含：

- 原文标题
- 原文链接
- 内容类型：体验/评测、横评/对比、吐槽/避坑、新品开箱等
- 内容短摘
- 二创切入
- 单篇分
- 关键词稳定分
- 评论/收藏/点赞
- 抓取时间

### 2. 给每个候选打二创分

`creative_score` 不按阅读量算，因为当前接口没有稳定返回阅读量。

它看的是更稳定的字段：

```text
关键词命中
来源可信度
内容类型
评论/收藏/点赞
近期性
是否包含具体型号
```

同时还有一个「关键词稳定分」：

```text
前 5 条平均单篇分 + 有效条数加成
```

这样可以避免某个品类只靠一篇互动异常高的文章冲到第一。比如「浴霸」曾经因为单篇互动高排到第一，但从稳定性看，洗地机、耳机、手机、NAS、键盘这类品类更适合长期追。

### 3. 写入飞书选题池

高分候选可以写入飞书多维表格，作为每日选题池。

这张表适合记录：

- 候选标题
- 原文链接
- 关键词和品类
- 内容类型
- 互动数据
- 二创切入
- 状态和后续处理记录

每日刷新时按原文链接去重，只做增补，不重复堆数据。

### 4. 用 Linkly AI 查本地资料（试点）

Linkly AI 作为本地资料检索层接入，适合查历史文章、产品说明书、品牌 brief、PDF 报告和本地竞品资料。

它不替代 zvec，也不参与外部热点抓取。

推荐分工：

| 工具 | 负责什么 |
|------|----------|
| Linkly AI | 本地文件全文检索、PDF/DOCX/Markdown/图片 OCR、写作前事实补充、质检反查 |
| zvec | 选题去重、角度库、风格锚点、内容流结构化记忆 |
| daily-hot-mcp / 什么值得买工具 | 外部热点和产品体验来源 |

试点阶段以 HTTP MCP 为主，不依赖 CLI：

```bash
codex mcp add linkly-ai --url http://127.0.0.1:60606/mcp
```

前置条件：

- Linkly AI Desktop 必须运行
- Linkly Desktop 已在「设置 → 文件夹」中添加至少一个监听目录；监听文件夹负责本地索引，是本地检索的必要条件
- 「知识库 / Libraries」只用于按主题组织或共享资料，是可选能力；`list_libraries` 返回空列表不代表本地检索不可用
- CLI 只用于诊断和本地调试，例如 `linkly status`、`linkly doctor`
- 暂不启用 Remote Tunnel；本机 Hermes/Codex 直连 `127.0.0.1`，不需要公网通道

可用性以一次真实的 MCP `search` 为准：Desktop 或 MCP 不通时标注「Linkly 本地资料不可用」；搜索调用正常但结果为空时标注「Linkly 本地资料未命中」。两种情况都继续用 web/search/zvec 降级，不要用 `list_libraries` 是否为空判断本地检索故障。

### 5. 用 zvec 做知识积累

仓库内置 zvec 知识库接口，用来做：

1. 选题去重
2. 历史角度检索
3. 竞品内容检索
4. 风格锚点检查
5. 混合检索

命令示例：

```bash
/tmp/zvec-poc/bin/python zvec/zvec_kb.py dedup "咖啡机为什么会吃灰" 0.65
/tmp/zvec-poc/bin/python zvec/zvec_kb.py search_angles "洗地机 发臭 避坑" 5
/tmp/zvec-poc/bin/python zvec/zvec_kb.py check_style "文章前500字" 5
```

## 运行方式

生成本地选题报告：

```bash
python sourcing-hotspots/scripts/smzdm_product_topics.py --output-dir output
```

会生成：

```text
output/smzdm_product_topics_report.md
output/smzdm_product_topics_items.json
output/smzdm_product_topics_rows.json
```

同步到飞书多维表格：

```bash
python sourcing-hotspots/scripts/smzdm_product_topics.py \
  --output-dir output \
  --sync-lark \
  --base-token <base_token> \
  --table-id <table_id>
```

创建飞书 Base：

```bash
cd sourcing-hotspots
scripts/create_lark_base.sh
```

安装每日刷新任务：

```bash
cd sourcing-hotspots
HERMES_TOPICS_PYTHON=/path/to/python \
scripts/install_daily_smzdm_topics_launchd.sh <base_token> <table_id>
```

默认每天 `09:20` 刷新一次。

## 这套流程怎么组织

这套流程按三层运行：

| 层级 | 角色 | 决策权 |
|------|------|--------|
| 主 Agent | 导演和制片人：理解用户目标、选择流程、串联产物、做最终取舍 | 唯一拥有流程选择和最终判断权 |
| Skill | 阶段 SOP：抓素材、筛选、角度、结构、标题、写作、质检、小红书适配 | 只定义规则、输入输出和检查清单 |
| 工具/数据源 | 执行层：daily-hot-mcp、什么值得买抓取、Linkly AI、搜索、zvec、飞书 Base | 只返回数据或执行动作，不独立决定选题 |

子 Agent 只在三种情况下启用：

- 多候选筛选：独立打分、提出反面理由，帮助主 Agent 避免拍脑袋。
- 质量审查：检查事实、结构、风格和平台规则。
- 多方案并行：同一个题目需要比较 2-3 个角度或结构方案。

其他阶段默认由主 Agent 顺序调用 Skill 和工具完成。这样链路更短，责任更清楚，也更容易排查问题。

## 中文呈现原则

这套流水线默认面向中文内容创作。无论上游资料、工具字段、GitHub 页面或浏览器环境是中文还是英文，所有面向用户的内容都必须用自然中文呈现。

- README、使用说明、变更记录和流程文档默认写中文。
- 阶段产物、飞书多维表格字段、选题理由、质检报告、发布汇报默认写中文。
- 代码标识、命令、文件名、API 字段可以保留英文，但解释和结论必须用中文。
- 不依赖浏览器自动翻译；需要英文版时单独维护 `README.en.md` 或英文附录。
